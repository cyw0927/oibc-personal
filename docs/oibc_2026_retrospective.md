> 구성: **1부**(1~13장)는 사용자 시점의 프로젝트 회고(Codex 작성), **2부**는 Claude의 기술 회고다. 2부는 1부와 겹치지 않도록 버전별 수치, 외부 예보 파이프라인, 실패 분석, Claude의 실수만 다룬다.

# OIBC 2026 태양광 발전량 예측 프로젝트 회고

## 1. 처음에는 대회가 무엇을 요구하는지도 몰랐다

이번 프로젝트는 태양광 발전소 253곳을 두 그룹으로 나누고, 각 그룹이 시간마다 얼마나 발전할지 예측하는 대회였다. 발전소 묶음을 VPP라고 불렀는데, 처음에는 이 말부터 어려웠다. 쉽게 생각하면 여러 발전소를 두 개의 바구니에 나눠 담고 바구니별 발전량 합계를 맞히는 것이다.

각 바구니에 담긴 발전소의 설비 용량 합계는 20MW 이상이어야 했다. 예측과 실제 발전량의 차이는 벌점으로 이어졌고, 전기 가격과 시간대에 따라 오차의 영향도 달라졌다. 내가 맡은 출발점은 발전소를 어떻게 묶을지, 그 결과의 정산금과 제출 파일을 어떻게 확인할지 살펴보는 일이었다.

나는 이 분야를 처음 접했다. 예측 모델, 데이터 검증, 잔차, 정산이라는 말도 그때그때 물어보며 배웠다. 프로젝트의 방향을 이해하려고 계속 질문했고, 코드를 작성하고 계산하는 일은 Claude와 Codex의 도움을 받았다.

## 2. 결과와 숫자를 읽는 법

2026년 11월 13일 22시 13분 리더보드 화면 기준으로 WATT NEXT는 학부생 부문 **167위**, 정산금 **6,462,653,869원**을 기록했다. 화면에는 성공 제출 17회가 표시됐다. 공유 작업 기록에는 이 결과가 마지막 v14s 후보의 점수로 적혀 있다.

앞서 확인한 v10의 정산금은 6,461,252,004원이었으므로 v14s는 **1,401,865원** 높았다. 이 금액은 대회의 점수에 해당한다. 실제로 내 통장에 들어온 돈이 아니다.

과거 데이터로 계산한 내부 검증 벌점과 공식 리더보드의 정산금도 서로 다른 숫자다. 처음에는 1~2월 내부 계산을 1년 평가 점수와 직접 비교하려고 했다. 그 뒤 평가 기간과 입력 자료가 같은지부터 확인해야 한다는 것을 배웠다.

## 3. 팀에서 시작한 일 — 그룹 조건부터 확인

처음 진행한 일감은 #989였다. 대회 자료와 설명을 살펴보면서 발전소 253곳을 두 그룹으로 나누는 조건과 20MW 제약을 정리했다. 규정에서 명확하게 확인한 내용과 팀원 또는 주최 측의 확인이 필요한 내용을 구분해 기록했다.

#990에서는 그룹이 조건을 만족하는지 검사하는 도구를 살펴보고 검증했다. 각 발전소가 빠지거나 중복되지 않았는지, 등록되지 않은 ID가 들어오지 않았는지, 용량이 정확히 경계에 걸렸을 때 올바르게 판정하는지를 확인했다. 기준 배정과 용량을 맞추는 다른 배정 방법도 비교했다.

발전소를 두 바구니로 나누는 일에는 조건이 함께 따라왔다. 모든 발전소가 한 번씩 들어가야 하고 각 바구니의 용량 조건도 만족해야 했다.

## 4. 정산 계산기와 잔차 검사

#991은 예측 결과가 정산금으로 어떻게 이어지는지 확인하는 일이었다. 실제 발전량과 예측 발전량을 그룹 단위로 합산한 뒤 오차와 벌점을 계산하는 구조를 살폈다. 전기 가격인 SMP, 시간대에 따른 가중치, 단위, 음수 발전 실적, 반올림 처리도 대조했다.

README를 바탕으로 계산기를 만들고 합성 자료로 계산을 시험했다. 공식 계산 기준과 완전히 일치하는지 확인되지 않은 부분은 잠정 결과로 기록했다. 이후 주최 측의 음수 실적 처리 답변을 받아 기존 구현과 대조하고 수정하는 작업도 진행했다.

#992에서는 다른 팀원이 만든 예측 결과를 받아 그룹 최적화에 연결했다. **잔차**는 실제 발전량과 예측 발전량의 차이다. 예를 들어 실제가 100, 예측이 80이면 실제에서 예측을 뺀 잔차는 20이다. 부호를 반대로 해석하면 그룹 비교 결과도 달라질 수 있어서 기준을 맞춰야 했다.

파일의 발전소 ID와 시간, 중복과 누락, 잔차 부호, 모델 버전과 SHA-256을 확인했다. SHA-256은 파일 내용이 같은지 확인할 때 쓰는 긴 지문이다. 팀원의 실제 자료가 도착한 뒤에는 합성 자료로 확인한 구조와 실제 예측 연결 결과를 구분해 기록했다.

## 5. 기존 그룹과 Swap 방식 비교

그룹을 바꾸면 벌점을 줄일 수 있을지 궁금했다. 그래서 기존 배정과 **Swap 방식**을 비교했다. Swap은 두 바구니에서 발전소를 하나씩 맞바꾸고, 용량 조건을 지키면서 벌점이 줄어드는 교환을 찾는 방법이다.

실제 과거 검증용 예측을 같은 조건으로 비교했지만, 한 달의 개선이 다음 달이나 다른 예측 모델에서도 유지되는 것은 아니었다. 예측 모델이 바뀌면 발전소별로 틀리는 패턴도 달라질 수 있었다. 모델별 비교에서 그룹 교환 효과는 약 −23만~+41만 원으로 나타났고, 예측 모델을 바꿨을 때의 차이는 그보다 큰 경우가 있었다. 이 숫자는 당시 비교한 **과거 2월 내부 결과**이며 연간 공식 수익 차이가 아니다.

이후 더 살펴본 결과에서는 두 그룹이 같은 방향으로 함께 틀리는 오차가 컸다. 그룹 구성만 바꿔 줄일 수 있는 부분이 제한적일 수 있다는 뜻이었다. 그래서 바구니 전체를 더 잘 예측하는 방법으로도 관심을 넓혔다.

## 6. 제출 파일을 만들고 검수하기

#993과 #1147에서는 제출 파일을 만들고 형식을 확인하는 작업을 진행했다. 발전소별 그룹을 적은 composition.csv와 그룹별 시간당 예측을 적은 forecast.csv를 준비하고, 시간축과 행 수, 누락·중복, 음수나 비정상 값, 그룹 용량을 검사했다.

팀에서 만든 검사와 공식으로 제공된 형식 검사기를 실행하고, 파일 지문과 결과를 정리해 팀원이 다시 확인할 수 있게 전달했다. 프로그램을 제출해 주최 측이 실행하는 줄 알았던 설명도 바로잡고, 우리가 준비한 CSV를 제출하는 흐름을 다시 확인했다.

팀원들이 독립적으로 대조할 수 있게 파일의 위치, 버전과 해시, 계산 방법도 공유했다. 수아님의 데이터·제출 독립 검토와 상재님의 예측 자료 인계, 튜터님의 판단이 이어져야 제출까지 연결될 수 있었다.

## 7. #1314 — 바구니를 직접 예측하는 시도

팀의 발전소별 예측에 더해 #1314는 **그룹 합계 자체를 예측하는 모델**을 함께 사용했다. 발전소마다 예측한 숫자를 더한 값과 바구니 전체를 직접 예측한 값을 섞는 방식이었다. 바구니 합계로 벌점을 계산하므로, 서로 다른 예측이 서로의 약점을 보완할 수 있는지 확인하려는 생각이었다.

초기 v2 후보는 발전소별 예측을 합친 값 40%와 그룹 직접 예측 60%를 섞었다. 공유 기록에 따르면 5차 제출은 6,436,427,653원이었다. 이후 팀 작업과 별도로 개인 저장소에서 여러 후보를 실험하고 확인하는 방향으로 작업을 이어갔다.

여기서 **OOF**라는 자료를 많이 사용했다. 모델이 학습에 직접 사용하지 않은 과거 구간을 대상으로 만든 예측 결과다. 과거 실제값과 비교할 수 있어 새 방법을 시험하는 데 도움이 된다. 같은 과거 구간을 계속 보고 방법을 고르면 그 기간에만 잘 맞는 방향으로 치우칠 수도 있다.

## 8. 데이터가 부족하거나 끊긴 발전소가 문제일까

기록이 없거나 낮에도 발전량이 0인 발전소를 계속 발전한다고 예측하면 오차가 커질 수 있다고 생각했다. 처음에는 이것이 상위권과의 격차를 설명할 유력한 원인일 수 있다고 예상했다.

기록과 과거 예측 자료를 다시 확인해 보니, 기록이 적다는 사실만으로 고장이나 폐지를 단정할 수 없었다. 첫 기록일도 실제 준공일이라고 확정할 근거가 부족했다. 일부 낮 시간에 0이 많은 발전소는 있었지만, 확인한 개발용 구간에서 실제 0을 미리 안다고 가정해 보정한 효과는 전체 벌점 약 1.5% 수준이었다. 이 계산은 실제값을 보고 나서 한 진단이어서 미래를 예측하는 방법 자체는 아니었다.

처음에 가능성을 너무 크게 말한 부분을 고쳤다. 기록이 없는 이유와 미래의 발전 여부는 별도로 확인해야 한다는 점을 배웠다.

## 10. v7부터 마지막 v14s까지

v7은 기존 모델의 예측과 발전소 그룹 구성을 개선하려는 과정에서 나왔다. 재검증할 때는 평가하는 달을 그룹 선택과 모델 학습에서 빼고 다시 계산했다. 다섯 달 비교에서 v6 대비 벌점은 평가 달만 제외한 방식으로 약 1.88%, 평가 달보다 과거 자료만 쓴 방식으로 약 0.89% 줄었다. 두 수치는 검증 방식이 다르며 공식 점수 개선을 보장하는 값은 아니다.

그다음에는 기상기관 예보를 고정된 넓은 지역의 평균으로 활용하는 후보를 검토했다. 발전소 좌표에 예보 격자를 직접 연결한 초기 v8에는 규정상 문제가 있다는 검토가 나와, 고정 지역 평균을 사용하는 v8-box로 바꿨다. 이후 GFS 예보도 결합한 v9, 입력을 더 확대한 v10 등을 비교했다.

외부 자료에 대한 기본 규정 문구와 별도 공지의 관계, 원본 공개 시각은 계속 확인이 필요했다. 광역 평균 사용 가능 여부를 공지 기록에서 검토하고 원본 저장소의 공개 시각과 예보가 가리키는 시간을 표본 대조했다. 일부 자료의 최초 공개 시각은 끝까지 전수 확인하지 못했다.

v11과 v12 이후에도 입력을 더 늘리거나 배합을 바꿔 봤지만, 과거 검증에서 좋았던 방향이 공식 점수에 그대로 이어지지는 않았다. v14에서는 기존 예측에 비슷한 과거 날의 예측과 물리 계산을 각각 5%씩 더했다. v14s는 그 구조에 여러 번 학습한 발전소 모델의 평균을 사용한 최종 후보였다.

마지막으로 기본 예측이 0인 시간을 모두 0으로 만들거나 이른 아침과 저녁의 보정을 빼는 방법도 살펴봤다. v14의 과거 11개월 대리 자료에서는 두 방법 모두 총 벌점이 늘어 채택하지 않았다. 기본 예측은 0이었지만 실제로 발전한 사례가 있어 일괄적으로 0을 만드는 규칙을 조심해야 했다.

## 11. Claude와 Codex를 함께 쓰며

처음부터 내가 모델을 설계하거나 코드를 직접 구현한 것은 아니었다. 내가 목표를 정하고, 이해할 수 없는 부분을 질문하고, 비교하거나 다시 확인할 일을 지시했다. Claude와 Codex는 코드 작성, 자료 분석과 계산, 문서 초안을 도왔다.

후반에는 Claude가 주로 새 모델 실험과 후보 제작을 맡고, Codex가 결과 재계산과 독립 검증을 맡도록 나눴다. 실제로는 둘 다 아이디어를 내고 실험과 검증을 수행한 적이 있어 역할이 완전히 분리된 것은 아니다. 공유 상태판과 각자의 작업 기록을 두고 서로 읽게 하면서, 한쪽이 놓친 조건이나 과장된 해석을 다른 쪽이 짚도록 했다.

이 방식에도 문제가 있었다. AI가 작업을 이어가다가 중단되면 어디까지 끝났는지 다시 확인해야 했고, 서로 다른 로컬 파일을 가리키거나 검증 상태를 다르게 이해하기도 했다. 그래서 파일 경로, 버전, 해시와 실행 결과를 남기는 일이 중요해졌다. 상태판은 도움이 됐지만 기록이 길어지고 오래된 상태와 새 상태가 섞이면 그 자체도 다시 확인해야 했다.

## 12. 아쉬웠던 점과 다음에 바꾸고 싶은 것

첫째, **문제와 평가 방식을 더 일찍 이해했으면 좋았겠다.** 처음에는 내가 무엇을 맡았는지, 팀의 예측과 내 그룹 작업이 어떻게 이어지는지 몰랐다. 다음에는 자료의 모양부터 입력, 예측, 그룹 합산, 벌점, 제출 순서까지 작은 예제로 이해하고 시작하고 싶다.

둘째, **실험을 시작하기 전에 멈추는 기준을 정해야겠다.** 점수가 기대보다 낮자 새로운 구조를 계속 시도했다. 여러 방법을 탐색한 경험은 남았지만, 같은 과거 기간을 반복해서 보고 선택했기 때문에 결과에 낙관이 섞였을 가능성도 생겼다. 다음에는 무엇을 바꾸고 어떤 기간에서 얼마만큼 나아져야 채택할지 먼저 정하겠다.

셋째, **제출 형식 통과와 파일 변화 확인을 각각 해야 한다.** 11차와 12차 제출 화면의 점수는 같았다. 화면의 숫자만으로 두 파일이 같다고 단정할 수는 없지만, 제출 전에는 이전 파일의 해시와 내용, 바뀐 행 수까지 확인하는 절차가 필요하다는 것을 배웠다.

넷째, **AI가 말한 것과 내가 실제로 확인한 것을 구분해야 한다.** 점수가 좋아질 가능성, 과거 자료에서의 개선, 사후에 정답을 알고 계산한 한계, 공식 점수는 각각 의미가 다르다. 앞으로는 어떤 자료로 무엇을 계산했는지, 다른 기간에도 적용할 수 있는지, 아직 모르는 것이 무엇인지 함께 기록하겠다.

## 13. 프로젝트를 마치며

이번 대회는 태양광 발전 예측을 처음부터 이해하며 따라간 프로젝트였다. 그룹 배정과 용량 검사에서 시작해 정산, 예측 결과 인계, 제출 파일 검증, 여러 모델의 비교와 최종 후보까지 이어졌다.

모든 시도가 점수 개선으로 이어지지는 않았다. 대신 실제 자료와 합성 자료를 구분하고, 예측에 쓸 수 있는 시점을 따지고, 같은 조건으로 비교하며, AI가 만든 결과도 다시 확인해야 한다는 것을 배웠다. 다음 프로젝트에서는 이 과정을 처음부터 더 차분하게 이해하고 설명할 수 있도록 진행하고 싶다.

## 16. 외부 예보 파이프라인을 만든 과정

규정(DataEn 2026-10-28 공지 §1·§3·§5) 때문에 세 가지를 지켜야 했다: 공개·상업 이용·재취득 가능한 자료, 전날 17:00 KST 이전 공개, 발전소 좌표로 격자를 고르지 않기.

1. **좌표 매칭에서 고정 박스로 (v8 → v8-box).** 처음엔 발전소마다 가장 가까운 ECMWF 격자를 붙였다가 §5 위반으로 판단해 버렸다. 34~38°N/126~130°E 박스와 북·남 반쪽 평균만 쓰도록 바꿨다. 성능은 −1.74% → −1.01%로 줄었지만 규정 안이다.
2. **GFS 시간별 (v10의 핵심).** 1° 파일, 00Z D−1 실행, 리드 21~36시간 → 대상일 04~21시. 6시간 평균값을 3시간 값으로 나누는 식(3h = 2·a6 − a3)을 썼다. 요청이 하루 60번 × 1,970일이라 다운로드 한 번에 약 3시간이 걸렸다.
3. **ECMWF는 AWS가 막혔다.** 앙상블·시간별 요청에 503이 계속 났다. 공식 Google Cloud 미러(storage.googleapis.com/ecmwf-open-data)를 찾았고, AWS와 같은 파일임을 원본 17건으로 확인했다.
4. **Windows가 GRIB 해독기를 막았다.** 11/13 오후부터 스마트 앱 컨트롤이 eccodes DLL을 차단했다. 보안 설정은 건드리지 않고 WSL 우분투 가상환경에 리눅스 패키지 파일을 풀어 우회했다.
5. **ECMWF 00Z 공개 시각 변화 발견.** 00Z 실행의 AWS 공개 시각이 **2025-10-02 실행부터 08:34 → 07:34 UTC(16:34 KST)** 로 당겨졌다(서머타임과 무관 — 10/26, 3/29 전후로 변화 없음). 그래서 평가 기간 중 **241일(2025-10-03~2026-05-31)** 은 더 최신인 전날 00Z를 규정 안에서 쓸 수 있었다. 다만 실험해 보니 효과는 ±0.05%였다(v15, 기각).

## 17. 실패를 숫자로 이해하기

- **그룹 배정은 더 손댈 데가 없었다.** v11 대리 예측 기준 벌점 176.48M 중 전체 합계 오차 하한이 175.36M(99.4%)이었다. 두 바구니가 같은 방향으로 틀려서 배정을 바꿔도 상쇄할 몫이 없다는 뜻이다.
- **정보를 더 넣을수록 나빠진 경우.** GFS 변수를 46개로 늘린 v12는 +1.19%(3/12)였다. 4구역 박스, 시간차 앙상블, 청명지수도 각각 +0.3~+2%였다. 기존 13개 변수와 같은 정보에 잡음만 더해졌다.
- **예보가 엇갈린 날 진단.** 세 GFS 실행(00Z·18Z·12Z)의 일사 차이로 날을 셋으로 나눴다. v11은 엇갈린 날에 −3.0%였지만 일치한 날에는 +1.9%였다. 쉬운 날까지 흔들었다는 점이 v11 실패를 설명하는 단서다.
- **v14s가 통한 이유.** 유사 기상일(AnEn)과 물리 모델은 단독으로는 v10보다 39%, 80% 나쁘다. 하지만 틀리는 방식이 달라서 5%씩만 섞으면 오차가 줄었다. 일출·일몰 무렵 기반 모델이 0으로 자른 시간도 메웠다(Codex 확인: 그런 301행 중 295행에 실제 발전이 있었다).
- **마지막 날 기각 목록:** 선형 MOS, AnEn 변형 4종, 발전소 단위 AnEn, 하루 총량 AnEn, 시간대별 비중, 조원 모델 혼합, v13(ECMWF 시간별 ML), v15(ECMWF 00Z). 모두 v14 대비 같은 행에서 비교했다.

## 18. Claude가 한 실수

1. **규정을 단정했다.** "외부 데이터 써도 된다"고 말했지만, 근거는 팀이 10/31에 남긴 기록이었다. 기본 규정(S03)과의 충돌도 미해결 상태였다. 사용자가 출처를 묻고 나서야 원문을 확인했다.
2. **긴 작업을 저장 없이 돌렸다.** ECMWF 앙상블 다운로드(메모리에만 보관 → 세션 종료로 유실), v15 검증(끝에서만 저장 → 프로세스 종료로 유실), 재시작하며 로그 덮어쓰기. 같은 실수를 세 번 했다. 지금은 "단계별 저장·이어받기·새 파일명"을 규칙으로 기록해 두었다.
3. **진행 확인을 미뤘다.** 다운로드가 12:51에 끝났는데 14시에야 알아챘고, 중복 실행된 체인도 늦게 발견했다.
4. **근거 없이 추정했다.** 조원 모델이 "25M 낮을 것"이라고 했다(실제 비교는 같은 조건 OOF로 해야 했다). 일출·일몰 값을 "오류"로 보고 마스크를 제안했는데, 실제로는 개선 요인이었다.
5. **너무 일찍 포기를 권했다.** 11/13 오후 "v11로 마무리하자"고 했지만, 사용자가 계속 밀어서 v14s(+1.4M)가 나왔다.

## 19. 다음 프로젝트에 남길 기술 체크리스트

- 실험 전에 **채택 기준을 숫자로 고정**한다. 예: 같은 행, 평가 월을 뺀 선택(LOMO), 기준 대비 −0.3% 이상, 과반 월 개선.
- **새 정보인지, 같은 정보의 재조합인지** 먼저 묻는다. 후자는 기대를 낮게 잡는다.
- 외부 자료는 **원본 공개 시각을 날짜별로 기록**한다(Last-Modified). 표본 검사보다 전수 기록이 싸다.
- 혼합은 **계열이 다른 모델을 작은 비중으로** 섞는다. 같은 모델 안에서 비율을 크게 옮기지 않는다.
- 다운로드·학습은 **단계별 저장과 이어받기**를 기본으로 하고, 백그라운드 작업은 중복 실행을 확인한다.
- 실험이 끝날 때마다 결과와 결정을 상태 파일에 한 줄씩 남긴다. 이번에 Codex와 서로 검증할 수 있었던 건 이 기록 덕분이었다.
